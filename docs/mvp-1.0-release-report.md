## 1. Verified Capabilities

### 1.1 Repository Scanning

- Directory walk up to `maxDepth=12` / `maxFiles=10000` with `.gitignore`-style ignore rules
- Symlinks skipped during scan; `.git`, `node_modules`, and the configured docs output directory excluded
- `truncated` flag set on `ProjectKnowledge` when scanner limits are hit

### 1.2 Technology Detection

- Languages detected: TypeScript, JavaScript, Python (and others via extension heuristics)
- Package managers detected: npm (requires `package-lock.json`), yarn, pnpm, bun
- Frameworks detected: Angular, React, NestJS, Node.js — all with confidence levels
- Technology plugins (angular, react, nest, node): detection implemented; framework-specific analysis declared as placeholder, documented in known limitations

### 1.3 Plugin Architecture

Five builtin analyzer plugins dispatched by `PluginManager`:

| Plugin ID | Role |
|---|---|
| `builtin.folder-analyzer` | Classifies and describes every scanned folder |
| `builtin.module-analyzer` | Discovers application, library, and feature modules |
| `builtin.dependency-analyzer` | Detects import relationships between modules |
| `builtin.convention-analyzer` | Extracts project conventions from PKM and config files |
| `builtin.navigation-analyzer` | Builds task-to-document navigation map for AI agents |

Four technology plugins (angular, react, nest, node) provide stack-specific detection.

`PluginRegistry` enforces unique plugin IDs. `mergePluginContributions` merges `PluginContributions` from all plugins without mutation.

### 1.4 Documentation Generation

Eight registered PKM-powered Markdown templates:

1. `architecture.md`
2. `folder-structure.md`
3. `dependency-map.md`
4. `conventions.md`
5. `agent-navigation.md`
6. `ai-context.md`
7. `implementation-guide.md`
8. `ai-readiness.md` (via `AI_READINESS_TEMPLATE`)

Generated files carry the protection marker `<!-- Generated by AI Project Docs. Safe to update. -->`. User-managed files without the marker are always preserved; they are never overwritten or deleted.

### 1.5 18-Step Declarative Pipeline

Pipeline declared as pure data in `src/domain/pipeline.ts`; executed by `src/core/pipeline-orchestrator.ts`; handlers looked up by name in `src/core/pipeline-handlers.ts`. Steps:

1. Resolve Configuration
2. Load Repository Metadata
3. Scan Repository Structure
4. Detect Technologies
5. Generate Documentation Plan
6. Build Project Knowledge ← PKM assembled here
7. Analyze Folder Knowledge
8. Analyze Modules
9. Analyze Dependency Graph
10. Analyze Conventions
11. Build AI Navigation Map
12. Analyze AI Insights (skipped unless `--ai`)
13. Detect Changes
14. Write Documentation
15. Validate Documentation
16. Calculate AI Readiness
17. Export Agent Context (skipped unless `--export-agents`)
18. Persist Project Knowledge

Default run (no `--ai`, no `--export-agents`): 16 completed, 2 skipped.

### 1.6 AI Readiness Score

- Deterministic 0–100 score; six weighted categories: repository structure, architecture knowledge, documentation coverage, agent navigation, project conventions, context maintainability
- Scoring rules versioned at `1.0.0`; identical PKM input always yields an identical score
- Results persisted to `ai-readiness.json` (machine-readable) and rendered as `ai-readiness.md` (human-readable)
- Validated immediately after writing; structural errors surface as validation failures (exit 2)

### 1.7 Incremental Change Detection

- Compares current PKM to previously persisted snapshot; records `change-summary.json`
- Derives `document-impact.json` to determine which Markdown files are affected
- Only impacted tool-managed files are rewritten on subsequent runs
- `ai-readiness.md` is recalculated and rewritten on every run (deterministic, timestamp updated)

### 1.8 Optional AI Enrichment

- Activated by `--ai` flag; requires `--openrouter-key` or `OPENROUTER_API_KEY`
- Enriches `architecture.md`, `ai-context.md`, `implementation-guide.md`, `agent-navigation.md` with non-authoritative insights
- AI failures never fail a deterministic run; invalid responses warn and continue
- `AIProvider` contract in `src/ai/providers/`; OpenRouter is the sole built-in provider
- Providers receive a compact PKM summary prompt — never source files, never secrets

### 1.9 Agent Exporters

- `generic` — outputs `AGENTS.generated.md` under `.ai-docs/agent-pack/`
- `cursor` — writes an always-on Cursor rule to `.cursor/rules/ai-project-docs.mdc`
- Both activated by `--export-agents [--target generic|cursor|all]`
- `claude`, `codex`, `copilot` are reserved IDs; planned post-1.0

### 1.10 CLI

- Argument parsing with full help text (`--help`)
- Exit codes: 0 success, 1 config error, 2 validation failure, 3 runtime error
- Optional AI analysis never downgrades a deterministic `0` exit to an error exit

## 4. Architecture Findings

### 4.1 PKM as Single Source of Truth — CONFIRMED

`ProjectKnowledge` (assembled at step 6 "Build Project Knowledge") is the exclusive input to all downstream steps. Generators, templates, and exporters consume PKM fields only — they do not re-scan the repository. Verified by code review of all template render functions and all plugin `analyze()` implementations.

### 4.2 Analyzer/Renderer Boundary — CONFIRMED

Analyzers (`src/analyzers/`) return structured data (`PluginContributions` or direct PKM fields). They do not generate Markdown strings. Renderers (`src/templates/`) produce Markdown from PKM data — they do not call `fs.readdir`, `fs.stat`, or any scanner functions.

### 4.3 AI Provider Boundary — CONFIRMED

`AIProvider.analyze()` receives a compact PKM summary string built by `PromptBuilder`. Source files, environment variables, and API keys are never included in the prompt payload.

### 4.4 Validator Boundary — CONFIRMED

`ValidateDocumentation` step reads files to check them; it does not write, delete, or rename any file.

### 4.5 CLI Thinness — CONFIRMED

`src/cli.ts` parses arguments and delegates immediately to `loadConfig()` (in `src/config/`) and `runPipeline()` (in `src/core/`). Business logic does not live in the CLI file.

### 4.6 Obsolete Placeholder Steps Removed — FIXED

Two placeholder pipeline steps ("Build Repository Model" and "Analyze Architecture") that had been declared as `status: 'pending'` with no real implementations were removed. The pipeline now has 18 steps (down from 20). The default run output correctly shows `16 completed, 2 skipped` instead of the previous `15 completed, 4 skipped`.

## 5. Security Findings

### 5.1 Path Traversal — CONFIRMED SAFE

All file writes go through `resolvePathWithinRoot()` in `src/utils/fs.ts`. The function resolves the target path and throws if the result escapes the repository root. Tested with `--docs-dir ../escape` and `--docs-dir /tmp/outside` in the release integration suite — both rejected with exit code `1` before any write is attempted.

### 5.2 Symlink Handling — CONFIRMED SAFE

Directory walker (`src/scanner/`) skips symlinks during tree traversal. Verified in unit tests.

### 5.3 API Key Handling — CONFIRMED SAFE

`--openrouter-key` value is stored in config and passed to the HTTP client. It is never logged, never written to disk, and never included in the PKM or any generated Markdown file. `PromptBuilder` does not include config fields in the prompt.

### 5.4 Source File Exclusion from AI Prompts — CONFIRMED SAFE

`PromptBuilder.buildAnalysisPrompt()` constructs the prompt from PKM metadata fields (module names, folder descriptions, technology names, conventions) — not from file contents. Verified by reviewing `src/ai/prompt-builder.ts`.

### 5.5 User File Preservation — CONFIRMED SAFE

`WriteDocumentation` step reads the existing file's first line before overwriting. If the protection marker is absent, the file is not touched. Tested in incremental fixture tests by creating a user file without the marker and confirming it survives a full run.

### 5.6 Source Code Immutability — CONFIRMED

No pipeline step, plugin, template, or exporter modifies source files in the target repository. All writes are confined to the configured docs output directory (`.ai-docs/` by default) and the optional agent export paths (`.cursor/rules/` for the Cursor exporter).

## 6. Performance Findings

Performance was assessed on the local repository (this codebase: ~70 TypeScript source files, ~100 total files excluding `node_modules` and `dist`).

- Full deterministic run (no `--ai`): completes in under 3 seconds on the CI container
- No synchronous disk I/O on the hot path beyond what Node.js requires for `fs.readdirSync` / `fs.readFileSync`

## 7. Fixed Release Blockers

### 7.1 Obsolete Pipeline Placeholder Steps

**Problem:** Pipeline declared 20 steps but steps 5 ("Build Repository Model") and 6 ("Analyze Architecture") had no handler implementations. They showed as skipped, confusing the run summary and tests.

**Fix:** Removed both placeholder objects from `ANALYSIS_PIPELINE` in `src/domain/pipeline.ts`. Pipeline reduced to 18 steps. `AGENTS.md` updated to reflect the correct step count and numbering. `README.md` updated to show the correct default run summary.

### 7.2 Version Numbers

**Problem:** `GENERATOR_VERSION` was `'0.1.0'`; technology plugin descriptors all used `'0.1.0'`; `package.json` was not yet at `1.0.0`.

**Fix:** Updated to `'1.0.0'` in `src/knowledge/constants.ts`, `src/plugins/technology/angular-plugin.ts`, `src/plugins/technology/react-plugin.ts`, `src/plugins/technology/nest-plugin.ts`, `src/plugins/technology/node-plugin.ts`, and `package.json`.

### 7.3 Test Fixtures

**Problem:** No end-to-end integration test fixtures existed. Unit tests covered individual modules but not the full pipeline on realistic repository structures.

**Fix:** Created three fixtures (`test/fixtures/fixture-typescript/`, `fixture-monorepo/`, `fixture-minimal/`) and 37 release integration tests in `src/release-integration.test.ts` covering all fixture scenarios, incremental behavior, path traversal rejection, and CLI contract.

### 7.4 Missing Lockfile in Fixture A

**Problem:** During integration test development, Fixture A's `package.json` alone did not trigger npm detection because `detectPackageManager()` requires a lockfile.

**Fix:** Added `test/fixtures/fixture-typescript/package-lock.json` (lockfileVersion 3, minimal valid format). No network access required — file is static.

### 7.5 ai-readiness.md Timestamp Volatility in Incremental Test

**Problem:** The test "generated docs remain stable across identical runs" failed because `ai-readiness.md` is always regenerated (even when the score is unchanged) because it embeds the generation timestamp.

**Fix:** Introduced `VOLATILE_DOCS = new Set(['ai-readiness.md'])` in the incremental test block. All other tool-managed Markdown files are compared byte-for-byte; `ai-readiness.md` is excluded from that comparison but its structural content (score, categories) is validated separately via `ai-readiness.json`.

### 7.6 Security Test Fixture Isolation

**Problem:** The "no output written outside target directory" test compared the fixtures directory before and after a CLI run, but a prior test session had already created `.ai-docs` inside the monorepo fixture, making the "before" snapshot non-empty and the assertion unreliable.

**Fix:** Rewrote the test to copy the monorepo fixture to an isolated temp directory, run the CLI there, and compare the fixtures root directory listing before/after — verifying that only the temp directory changed.

### 7.7 README Stale Claims

**Problem:** README's pipeline example showed `15 completed, 4 skipped` (correct for the old 20-step pipeline). "What it does not do yet" section incorrectly stated the Cursor exporter was unimplemented.

**Fix:** Updated pipeline example to `16 completed, 2 skipped`. Replaced the Cursor claim with the accurate statement that `claude`, `codex`, and `copilot` exporters are planned post-1.0.

## 8. Known Limitations

These limitations are documented in `README.md` and `CHANGELOG.md`. They are architectural trade-offs, not bugs.

| Limitation | Notes |
|---|---|
| Full scan on every run | Only Markdown regeneration is selective via incremental change detection |
| AI analysis opt-in | `--ai` required; only OpenRouter supported as a provider |
| Agent exporters | Only `generic` and `cursor` implemented; `claude`, `codex`, `copilot` are reserved |
| Technology plugins | Angular, React, NestJS, Node.js detection only; framework-specific analysis is a documented placeholder |
| Scanner limits | `maxDepth=12`, `maxFiles=10000`; `truncated` flag set on PKM when hit |
| No file watching | No Git hooks, no remote dashboard — run on demand |
